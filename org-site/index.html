Consent-first messaging

No message is delivered until the recipient has explicitly allowed the sender.

Alfred is feminist-informed software: consent, agency, and clear boundaries are architectural choices, not optional privacy modes. It ships as a Flutter web app (installable PWA) backed by Supabase, with Python bridges planned for federation. The supported client surface today is the web — not native mobile or desktop apps.

Try the live app View source

What makes Alfred different

Most messengers treat “block unknown senders” as a setting. In Alfred, filtered reception is always on: your personal allow list (persone consentite) gates delivery. An empty list means nothing is delivered. Senders who are not allowed get a single checkmark at most — silent rejection, no spam folder theatre.

Address-based chat

You message an address (username or user@server), not a rubrica entry. Contacts are optional and isolated from who can message you.

Server-side truth

Multi-device cloud client: delivery ticks (✓ / ✓✓) reflect platform state — delivered means accepted into the recipient’s archive on the server, not merely “pushed to a phone”.

Spec-driven

Product behaviour is captured in a promise registry (SYSTEM / PRODUCT / SURFACE) with DDD, UML, and client statecharts — built for clarity and review, including AI-assisted development.

Product today

Stable on main. Federation bridges exist as health-check stubs only.

Accounts & identity

  • Live Email + password auth; public username (email hidden from search)
  • Live Multi-account manifest; one active GoTrue session (focus) at a time
  • Live User and group account types
  • Live Profile, avatar, shareable #username / #username/chat links

Messaging

  • Live Inbox aggregated on-read; realtime chat by peer_profile_id
  • Live Text, GIF, voice (WebM), photo, video, static location
  • Live Delivery status ticks; emoji reactions; @username mentions
  • Live Optimistic send queue with retry on the client

Consent & social graph

  • Live Personal allow list — always enforced server-side
  • Live Optional contacts address book (separate from messaging)
  • Live Peer profile overlay: allow toggle, contact, share, start chat
  • Live On-demand search in inbox, contacts, and allow list

Groups & notifications

  • Live Group accounts with broadcast; participation via mutual allow list
  • Live Author attribution in group chats
  • Live Web Push (VAPID) with multi-account scope
  • Planned XMPP and Matrix federation via stateless bridges

Architecture

Flutter talks only to Supabase (Postgres, Auth, Realtime, Storage). Bridge daemons are stateless; platform state lives in the database.

Get started

Prerequisites: Flutter stable, Dart 3.12+, Git. Optional: Docker + Supabase CLI for an isolated local backend.

git clone https://github.com/alfred-im/alfred-im.git
cd alfred-im/client
flutter pub get
flutter run -d web-server --web-port=8080 --web-hostname=0.0.0.0

Open http://localhost:8080/. For local Supabase: supabase start from the repo root, then point the client at the local URL and anon key — see the repository README.

Before contributing, run cd client && bash scripts/verify.sh (CI gate).

Contribute & security

Bug reports and discussion: GitHub Issues. Pull requests are welcome when they align with the project’s direction and update specs when behaviour changes (Spec-Driven Development).

Please read the Code of Conduct. Do not report security vulnerabilities in public issues — use GitHub Security Advisories.
